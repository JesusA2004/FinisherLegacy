# Finisher Legacy API v1

Base URL: `/api/v1`

El contrato que consumirán la app iOS/Android, otros sitios de Finisher Legacy, y — desde Slice 6 — un futuro Desktop/Mobile para el personal operativo (Event Ops). Cada endpoint reutiliza los mismos Actions/Services/Queries/Policies/Form Requests que la web Inertia — nunca hay lógica de negocio duplicada entre transportes. Ver `docs/api/use-case-matrix.md` para el inventario completo de qué caso de uso vive en qué transporte.

Este documento cubre el **API general** (auth, medallas, eventos, Event Ops, integraciones). El **Device API** (`/api/v1/devices*`, `/api/v1/device*`, `/api/v1/production/*`) tiene su propio contrato, ya documentado en `docs/device-api/v1.md` — más abajo solo se referencia, no se repite.

## Autenticación

Autenticación por token vía [Laravel Sanctum](https://laravel.com/docs/sanctum) (tokens personales, no cookies de sesión). Cada request autenticado debe incluir:

```
Authorization: Bearer {token}
```

Los tokens no expiran automáticamente (configurable en `config/sanctum.php`). El cliente es responsable de invalidarlos vía `POST /auth/logout` cuando el usuario cierra sesión. Un token de `User` nunca autentica una ruta de Device API y viceversa (`App\Http\Middleware\EnsureUserToken` / `EnsureProductionDeviceToken`) — ver `docs/adr/0002-device-production-api.md`.

## Formato de respuesta

**Éxito (recurso único / acción):**

```json
{
  "data": {},
  "message": "Mensaje opcional en español, o null",
  "meta": { "request_id": "..." }
}
```

**Éxito (listas paginadas):** formato estándar de Laravel API Resources — nunca envuelto dos veces.

```json
{
  "data": [],
  "links": { "first": "...", "last": "...", "prev": null, "next": null },
  "meta": { "current_page": 1, "last_page": 3, "per_page": 20, "total": 45 }
}
```

## Errores (Slice 6 — unificado)

**Todo error que no sea de validación** — 401/403/404/409/429/500 — usa el mismo sobre en cualquier ruta bajo `/api/v1/*` (Device API incluido, con su propio catálogo de códigos):

```json
{
  "error": { "code": "NOT_FOUND", "message": "Recurso no encontrado.", "details": {} },
  "request_id": "..."
}
```

`App\Support\Api\ApiExceptionRenderer` es el único lugar que hace esta conversión (Domain Exception Mapper) — ningún controller tiene su propio try/catch a JSON. Cualquier excepción que extienda `App\Exceptions\Api\ApiException` se renderiza automáticamente con su propio código/status (p. ej. `App\Exceptions\PlateAlreadyExistsException` → 409 `PLATE_ALREADY_EXISTS`).

**Decisión deliberada — validación (422) NO se unifica**, se deja el formato estándar de Laravel:

```json
{
  "message": "Los datos proporcionados no son válidos.",
  "errors": { "email": ["El campo email es obligatorio."] }
}
```

Cambiarlo habría roto el manejo de validación de cualquier cliente existente sin beneficio real — es ya una forma bien conocida y normalizada (§49 del prompt Slice 6 permite explícitamente esta elección).

| Status | Código (`error.code`) | Significado |
|---|---|---|
| 200/201/202/204 | — | Éxito |
| 401 | `UNAUTHENTICATED` | Token ausente/inválido |
| 403 | `FORBIDDEN` | Autenticado pero sin permiso |
| 404 | `NOT_FOUND` | No encontrado |
| 409 | `CONFLICT` (o un código específico, p. ej. `PLATE_ALREADY_EXISTS`) | Conflicto |
| 422 | *(formato Laravel estándar, ver arriba)* | Validación fallida |
| 429 | `TOO_MANY_REQUESTS` | Límite de solicitudes excedido |
| 500 | `INTERNAL_ERROR` | Error interno — nunca expone stack trace |

## Request ID

Toda respuesta bajo `/api/*` trae un header `X-Request-ID` — reutiliza el que mande el cliente (`X-Request-ID` en el request) o genera un UUID. Útil para correlacionar logs con soporte a un futuro Desktop/Mobile (`App\Http\Middleware\AssignRequestId`). También aparece en `meta.request_id` (éxito) y `error.request_id`... (dentro del sobre de error, como `request_id` top-level).

## Idempotencia

Escrituras críticas aceptan un header `Idempotency-Key` opcional — una segunda solicitud con la misma clave repite la respuesta original en vez de re-ejecutar la acción:

- Device API: ya existente desde Slice 1/2 (`App\Http\Middleware\EnsureIdempotencyKey`, tabla `device_idempotency_keys`).
- API general (`event-ops/participants/{id}/plate` por ahora): `App\Http\Middleware\EnsureApiIdempotencyKey`, tabla `api_idempotency_keys` — mismo patrón, generalizado a cualquier actor Sanctum (`User` o `ProductionDevice`), nunca dos implementaciones incompatibles.

## Identificadores públicos

Las URLs nunca dependen de IDs incrementales predecibles cuando el recurso es sensible o público:

- **Medallas**: `uuid` (no el `id` autoincremental).
- **Legacy Code**: `code` (p. ej. `Q8K2MX7P`), atemporal.
- **Eventos**: `slug`.
- **Perfiles**: `username`.

IDs incrementales siguen usándose para recursos internos/operativos (`EventEdition`, `EventParticipant`, `ExternalSyncRun`, `ProductionJob`) — solo alcanzables con permiso de staff, no navegación pública.

## Fechas

ISO 8601 para timestamps. Fechas sin hora (`event_date`) en `YYYY-MM-DD`. Los endpoints de Event Ops devuelven varios timestamps como texto relativo (`diffForHumans()`, p. ej. "hace 4 segundos") en vez de ISO — igual que la web Inertia de la que reutilizan el mismo Resource, para no tener dos formatos de fecha para la misma pantalla.

## CORS

`config/cors.php` — sin orígenes permitidos por defecto (`FINISHER_CORS_ALLOWED_ORIGINS`, lista separada por comas). Nunca `*` combinado con `supports_credentials: true`. Sanctum token auth no depende de cookies para `/api/v1/*`, así que CORS solo importa el día que exista un cliente JS en otro origen.

## PII (Slice 6 audit)

Ningún endpoint de Event Ops/Device API devuelve `email`, `phone`, o `birth_date` de un participante — ni en búsqueda ni en detalle. El Device API ya cumplía esto desde Slice 1/2 (auditado, sin cambios necesarios); Event Ops (Slice 6, nuevo) se diseñó así desde el inicio.

## Versión

`GET /health` y `GET /device/bootstrap` devuelven `api_version` (`config('finisher.api_version')`, hoy `"1.0"`) y `minimum_supported_client_version` (nullable, sin aplicar todavía — preparado para cuando exista un cliente real que rechazar). Un bump de `api_version` implica un cambio incompatible; añadir un endpoint nunca lo requiere.

## Rate limiting

| Limiter | Aplica a | Límite |
|---|---|---|
| `api` (default) | Endpoints autenticados generales | 60/min por usuario o IP |
| `api-register` | `POST /auth/register` | 5/min por IP |
| `login` (compartido con la web) | `POST /auth/login` | 5/min por email+IP |
| `api-legacy-lookup` | `GET /legacy-codes/{code}` | 30/min por IP |
| `api-claim` | `POST /legacy-codes/{code}/claim` | 10/min por usuario |
| — | `GET /event-ops/{edition}/participants/search` | 60/min |
| Device heartbeat | Device API | sin límite agresivo — una estación operativa legítima nunca debe toparlo (ver `docs/device-api/v1.md`) |

## Auth

### `POST /auth/register`

Crea un usuario, le asigna el rol `athlete`, emite su Legacy ID y un token de API. Misma acción (`App\Actions\Fortify\CreateNewUser`) que el registro web.

### `POST /auth/login`

**Body:** `email`, `password`. **200** → `{ data: { user, token } }`.

### `POST /auth/logout` 🔒

Revoca el token actual.

### `GET /me` 🔒

Devuelve el usuario autenticado — `athlete` (resumen mínimo, si está vinculado) y `permissions` (nombres de permiso de `App\Support\PermissionCatalog`, nunca inferidos de un nombre de rol).

## Event Ops API 🔒 (Slice 6, nuevo)

Requiere permiso `operator.access` (el mismo que la web `/operator`). Ver `docs/adr/0006-event-operations.md` y `docs/api/use-case-matrix.md`.

### `GET /event-ops/{eventEdition}`

Dashboard operativo — `App\Queries\Operations\GetEventOperationsDashboard`, misma Query que la web. `data.readiness`, `data.metrics`, `data.production`, `data.stations`, `data.provider`.

### `GET /event-ops/{eventEdition}/participants/search?q=`

Búsqueda por dorsal/nombre — `App\Queries\Operations\SearchEventParticipants`, misma Query/prioridad (dorsal exacto → prefijo → id externo → nombre) que la web. Máximo 20 resultados. Nunca PII.

### `GET /event-ops/participants/{eventParticipant}`

Ficha completa: resultado + splits, resumen mínimo de Athlete, placa existente, elegibilidad (`App\Services\PlateEligibilityService`, Slice 4, reutilizado).

### `POST /event-ops/participants/{eventParticipant}/plate`

Genera la placa integrada — `App\Services\PlateGenerationService::generateIntegrated()`, el mismo Use Case que Event Ops web. **201** con la placa creada. **409** `PLATE_ALREADY_EXISTS` en un segundo intento — usa `Idempotency-Key` para que un reintento de red replique la respuesta en vez de fallar.

## Integraciones — Sync API 🔒 (Slice 4/6)

Requiere `integrations.view` (lectura) / `integrations.sync` (disparar). Ver `docs/adr/0005-unified-event-ingestion.md`.

### `POST /integrations/mappings/{eventMapping}/sync`

Encola `App\Jobs\SyncExternalEventJob` — nunca llama al proveedor externo en el request. **202 Accepted** con `{ mapping_id }`. Body opcional: `sync_type` (`roster`/`results`/`full`), `full` (bool).

### `GET /integrations/mappings/{eventMapping}/sync-runs/latest`

El `ExternalSyncRun` más reciente para ese mapping. **404** si todavía no ha corrido ninguno.

### `GET /integrations/sync-runs/{syncRun}`

Un `ExternalSyncRun` por id — mismo `App\Http\Resources\Api\V1\Integrations\SyncRunResource` que alimenta la página web de sincronización.

## Lo que falta (deuda conocida, no bloqueante)

- Scopes/abilities granulares por token de `User` (hoy todo token de usuario tiene acceso completo a las rutas de ese usuario — sin caso de uso real todavía que pida menos).
- `OverrideEventResult` como Action explícita separada — hoy la corrección manual de resultados vive dentro de `App\Actions\Integrations\IngestEventResult` (respeta `manual_override_fields`), sin una Action/endpoint dedicado para que un humano la dispare directamente vía API o Web todavía.
- Resultado API de solo-lectura para `EventResult`/splits fuera del contexto de Event Ops (hoy solo se leen dentro de `participants/{id}`).
